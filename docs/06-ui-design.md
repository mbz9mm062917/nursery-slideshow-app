# UI設計

## 1. 共通レイアウト: `WizardLayout`

全ウィザード画面（アップロード〜ダウンロード）は共通の`WizardLayout`コンポーネント（`components/common/WizardLayout.vue`）で包む。

```
┌─────────────────────────────────────────┐
│ [アプリ名]        STEP 3 / 9  ●●●○○○○○○  │ ← ヘッダー（現在地の可視化）
├─────────────────────────────────────────┤
│                                         │
│         画面固有のコンテンツ               │ ← 各Viewが差し込まれる領域
│                                         │
├─────────────────────────────────────────┤
│ [← 戻る]                    [次へ →]     │ ← フッター（全画面で同じ位置・同じ見た目）
└─────────────────────────────────────────┘
```

**設計理由**: 「戻る／次へ」の位置と見た目を全画面で完全に統一することが、PC操作が苦手なユーザーへの最大の配慮になる。画面ごとにボタン位置やラベルが変わると、それだけで迷いの原因になる。「次へ」はその画面の入力が未完了の間は非活性（グレーアウト）にし、押せる状態かどうかを見た目だけで判断できるようにする。進捗ドット（`STEP 3/9`）により、残り工程数が一目で分かり、心理的な負担を減らす。

ホーム画面・動画生成中画面・ダウンロード画面はウィザードの「開始点」「処理待ち」「終着点」であり、戻る/次への概念が薄いため`WizardLayout`は使わず、専用のシンプルなレイアウトにする（無理に共通化しない）。

## 2. 画面ごとの設計

### 2.1 ホーム画面（`HomeView`）

- 中央に「＋ 新しいスライドショーを作る」の1つの大きなボタンのみを配置する。
- 過去のプロジェクト一覧や設定メニューなどは一切置かない（MVPのスコープ外機能を匂わせる情報も出さない）。
- ボタン押下時に`POST /api/projects`を呼び、写真アップロード画面へ遷移する。

### 2.2 写真アップロード（`PhotoUploadView`）

- 画面上半分に大きなドラッグ＆ドロップ領域（「ここに写真をドラッグ、またはタップして選択」）。
- 画面下半分にアップロード済み写真のサムネイルグリッド。各サムネイルにタップで削除できる「×」を重ねて表示する。
- 上部に「42枚選択中」のようにシンプルな件数表示のみ行う（進捗バー等は不要）。
- 対応外の形式（jpg/jpeg/png以外）が混ざっていた場合は、その場でエラーメッセージ（画面上部のバナー）を出し、対応形式のファイルのみ取り込みを継続する（一部エラーで全体を止めない）。
- 「次へ」は1枚以上アップロード済みで活性化。

### 2.3 写真並び替え（`PhotoReorderView`）

- サムネイルグリッドをドラッグで並び替え可能にする（`components/wizard/PhotoSorter.vue`、ドラッグ操作ライブラリを利用）。
- 冒頭に一言ガイド「写真をドラッグして順番を並び替えられます」を表示する。
- 100〜300枚を想定するため、スクロール表示のみとしページングは行わない（一覧性を優先。パフォーマンスは通常のブラウザスクロール＋遅延読み込みで十分対応可能と判断し、仮想スクロール等の追加実装はMVPでは行わない）。

### 2.4 タイトル入力（`TitleInputView`）

- 画面中央に大きなテキスト入力欄を1つだけ配置する。
- プレースホルダーに具体例（「さくら組 運動会」）を薄く表示し、何を入力すればよいか直感的に伝える。
- 文字数上限（50文字）を入力欄の下に小さく表示する。

### 2.5 テーマ選択（`ThemeSelectView`）

- テーマをカード形式（サムネイル画像＋テーマ名）で並べる。選択中のカードは太い枠線と色で強調する。
- PCでは横4列、タブレットでは横2列のグリッド（レスポンシブ方針は§4）。
- カードをタップした瞬間に選択状態が確定し（決定ボタンを別途押す必要はない）、「次へ」が活性化する。

### 2.6 BGM選択（`BgmSelectView`）

- 曲名（明るい／感動／元気）をリスト形式で表示し、各行に試聴用の再生ボタンを置く。
- 選択はラジオボタン形式で1曲のみ選べる。
- 試聴は`<audio>`要素で行い、別の曲を再生すると前の再生は自動停止する（同時再生を防ぐ）。

### 2.7 スライド時間設定（`DurationSelectView`）

- 「3秒」「5秒」「7秒」を3つの大きなトグルボタンで横並び表示する。選択肢が少ないため、ドロップダウンではなくワンタップで選べるボタン形式にする。

### 2.8 プレビュー（`PreviewView`）

- これまでの入力内容（タイトル・テーマ名・BGM名・スライド時間・写真枚数）をサマリーカードで表示する。
- 加えて、先頭数枚の写真に選択中テーマのフレームを重ねた静止画イメージを並べ、大まかな雰囲気を確認できるようにする。
- **設計上の判断**: MVPでは「実際に動画をレンダリングしたプレビュー動画」は作らない。動画プレビューを用意すると、本生成とは別にFFmpegを実行する処理が二重に必要になり、実装・待ち時間の両面でコストが増える。要件⑧「生成前に内容を確認できる」は、設定内容のサマリー表示と代表写真への静的なテーマ適用イメージで十分に満たせると判断し、この方式を採用する。
- 「この内容で動画を作成する」ボタン押下で`POST /api/projects/{id}/video-jobs`を呼び、動画生成中画面へ遷移する。

### 2.9 動画生成中（`VideoGeneratingView`）

- 中央に大きな進捗バー（0〜100%）とアニメーションアイコン、「動画を作成しています…」の文言のみを表示する。他の操作は一切置かない（ユーザーを待たせる間に迷わせる要素を作らない）。
- `GET /api/video-jobs/{jobId}`を一定間隔でポーリングし、`progress`をバーに反映する。`status`が`COMPLETED`になったら自動的にダウンロード画面へ遷移する。
- `status`が`FAILED`になった場合は、進捗バーをエラー表示に切り替え、`errorMessage`を表示した上で「もう一度作成する」ボタン（プレビュー画面へ戻る）のみを提示する。

### 2.10 ダウンロード（`DownloadView`）

- 「動画が完成しました」というメッセージと、大きな「ダウンロード」ボタンを中央に配置する。
- 完成した動画をその場で確認できるよう、`<video controls>`でのインライン再生も併せて置く（実装コストがほぼゼロで、ダウンロード前に内容を確認できる安心感につながるため採用）。
- 「新しいスライドショーを作る」ボタンでホーム画面に戻れるようにする。

## 3. エラー表示の共通方針

- 共通コンポーネント`components/common/ErrorBanner.vue`を用意し、画面上部に赤系の帯でエラーメッセージを表示する形式に統一する（モーダルによる遮断は多用しない。作業の流れを止めすぎないため）。
- メッセージは常にAPI設計（Step5）で定めた`message`フィールドの日本語文言をそのまま表示し、専門用語やエラーコードはユーザーには見せない。

## 4. レスポンシブ方針

- PC優先で設計し、コンテンツ幅は最大960px程度に収め左右中央寄せにする。
- タブレット（横幅768〜1024px程度）では、グリッド列数を減らす（テーマ選択: 4列→2列など）以外はレイアウト構造を変えない。
- ボタンはタップ操作を考慮し、最小44×44px相当のタップ領域を確保する。
- スマートフォン単体での利用はMVPの対象外とする（要件どおりPC優先・タブレット対応まで）。

## 5. 配色・アイコン方針

- UIのクローム（ヘッダー・フッター・ボタン等）は、選択中のテーマに関わらず常に同じ配色（プライマリカラー1色＋アクセント1色＋グレースケール）に固定する。テーマごとの色味は「動画に反映される演出」としてのみ表現し、アプリの操作画面自体は色を切り替えない。
- **理由**: テーマに合わせてアプリ全体の配色まで変えると、保育士から見て「操作の一貫性」が失われ、ボタンの場所を毎回探すことになりかねない。UIの見た目は常に一定にし、色数を抑えるという非機能要件を満たす。
- 各ステップの見出しには、内容を直感的に示すアイコン（写真・並び替え矢印・テキスト・パレット・音符・時計・虫眼鏡・フィルム・ダウンロード矢印など）を1種類のアイコンセットで統一して使用する。
